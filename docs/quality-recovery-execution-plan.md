# VoiceType 质量收敛与 v0.8.0 发布执行书

状态：待执行。依据：2026-09-29 对工作区相对 origin/main 的完整审查。适用范围：当前未提交的 WebView2 主界面、模型修复、热键、更新结果展示、打包与发布流程。本文是执行与验收标准，不代表相关代码已经修好或已发布。

## 0. 目标、边界和完成定义

本轮目标是一次性关闭已发现的缺陷，并建立能持续拦截同类回归的工程门禁。软件无法承诺“从此绝无故障”；可执行的承诺是：每项关键行为有唯一契约、每个已知失败场景有自动化或真机验收、任何缺失证据都会阻止发布。不能用“编译通过”代替“功能通过”，不能以重跑碰巧变绿代替修复。

完成必须同时满足以下全部条件：

- 本文第 2 至 7 节的交付物全部落地，没有标记为待办或跳过的项目。
- 本文第 8 节的每个场景都有通过记录；失败、未运行、环境不满足都按未通过处理。
- Windows 可交互桌面上完成主界面与两种安装形态的验证，证据与待发布提交的 SHA 对应。
- 版本、公告、tag、三种产物和三份 SHA-256 清单一致；便携版与安装版的热更新均实测成功。
- 发布后按第 10 节确认线上 Release 和真机热更新；如失败，立即按既定回退或补丁流程处置。

本轮不改变热更新协议：GitHub Release 固定资产名、URL 前缀限制、下载与落盘双重 SHA-256 校验、install.mode 形态标记、模型随 exe 内置、模型目录优先级均必须保留。不得重新加入应用内模型下载。

## 1. 已确认的根因与架构决策

### 1.1 根因

1. 模型模块把“文件名存在”“字节完整”“识别引擎可初始化”当成不同概念，却都被某些调用方解释为“就绪”。当前 models_ready 只检查文件存在；指定模型目录下的 ensure_models_extracted 也据此跳过修复。已有单元测试把内容为 test 的伪 ONNX 文件判为就绪，说明测试本身固化了错误契约。
2. HTML、WebView IPC、Win32 窗口过程、录音与注入器分别决定一部分行为，没有统一的动作结果和焦点目标。于是录音按钮可以在自身窗口获得焦点时启动注入，更新结果可以写到不可见页面。
3. 只有 tag／手动触发的 release.yml；没有提交阶段的完整 Windows 门禁，也没有可交互桌面的 UI 验收。已有测试集中在底层逻辑与发布文件格式，不能证明新主界面的实际行为。
4. 文件替换和热键变更缺少事务边界：中间步骤失败后，磁盘或内存可能停在半完成状态。

### 1.2 本轮架构选择

保留 Win32 托盘与录音主线程，保留 WebView2 作为现代界面；不做整仓框架迁移。新增一个由 UI 线程拥有的应用控制层：HTML 和原生备用窗口只发类型化动作并显示状态，模型、录音、热键、更新的决策集中在控制层。耗时操作在后台执行，通过消息回主线程提交结果。

这是一项架构修复，而非继续在 settings_web.rs、ui_main.rs 和 HTML 三处各加一层条件判断。若第 8 节的桌面验收无法在可重复的 Windows 测试环境运行，或者无 WebView2 时无法提供可用备用界面，则停止 v0.8.0 发布；届时撤回 WebView2 界面，基于同一控制层恢复原生 Win32 界面。不得带着未验证的新界面发版。

### 1.3 审查问题与验收闭环

- 首页按钮向自身窗口注入：B2 改交互与绑定目标；8.2 的双窗口测试验收。
- 损坏模型被判为就绪、显式目录跳过修复：A1/A2 统一状态与事务；8.1 的同尺寸损坏和修复测试验收。
- 更新结果进入隐藏页面：C1 拆分事件并显示持久结果；8.3 的多页面与托盘场景验收。
- 高 DPI 裁切、WebView2 缺失时设置不可用：C2 自适应尺寸与原生备用界面；8.2 的缩放和无 Runtime 测试验收。
- 热键保存失败后的内存／注册表不一致：B3 事务回滚；8.2 的保存失败与重启测试验收。
- 删除旧模型后替换失败导致模型缺失：A2 可恢复替换；8.1 的故障注入测试验收。
- 0.7.0 版本与 tag 已使用、安装包和完整发布链未验收：D/E 建立提交和发布门禁；8.3/8.4 的六资产与双形态热更新验收。package.ps1 的 OutDir 与 installer.iss 固定 dist 不一致，也纳入 E 修复，确保隔离打包不混入旧文件。

## 2. 工作包 A：统一模型有效性、选择与修复

涉及 apps/tray/src/models_dl.rs、main.rs、ui_main.rs、settings_web.rs；允许抽出 model_manager.rs。先完成此工作包，再接 UI。

### A1. 一个模型状态契约

- 建立 ModelStatus，至少区分：Checking、Ready（含实际使用目录和模型版本）、Missing、Corrupt（含具体文件与原因）、PermissionDenied、Repairing、Unavailable。
- 建立唯一入口 inspect_model、ensure_model、model_config。启动、自检、录音入口、设置页状态和“重新检查”按钮都调用这一套逻辑。删除调用方自行组合 find_model_files、find_vad_model、root_has_model 来推断“就绪”的分支。
- 当前内置模型的五个文件以随代码维护的文件名、长度、SHA-256 清单校验；内容错误时不得返回 Ready。旧模型如继续兼容，也必须通过可信校验或真实 ASR/VAD 初始化，不能仅凭文件名。明确当前模型优先、旧模型仅作兼容回退。
- 模型目录解析保持原优先级：VOICETYPE_MODEL_DIR > exe 旁 models > LOCALAPPDATA/VoiceType/models > 工作目录 models。显式指定目录出错时给出该目录的明确错误，不偷偷改用别的目录；默认路径在 exe 旁不可写时才按既有规则转到用户目录。
- 界面只展示上一次已完成校验的状态；打开界面或录音事件刷新 UI 不重复同步读取约 50 MB 模型。启动、手动检查、修复后和每次新录音前触发验证；验证期间显示 Checking，不能把旧的 Ready 当成新检查结果。

### A2. 修复是事务

- 新内容先写同目录唯一临时文件、flush/sync、计算并核对 SHA-256，再替换目标。替换失败后必须保持旧文件可读，或从备份恢复；不能先删除唯一旧文件再尝试 rename。
- 用可注入的文件操作接口模拟创建、写入、同步、校验、替换、清理各步骤失败。每一步都断言最终状态：Ready，或带明确错误且没有被误判为 Ready；临时文件不会被下一次当作模型。
- 两个进程同时自检或修复同一目录时，使用目录级互斥或等价机制；第二个进程等待并复核结果，不互相删除文件。
- 模型修复与实际引擎初始化在后台进行。UI 线程不得同步散列大文件、写模型或启动识别引擎。失败在设置页保留可见状态，诊断日志记录错误码与路径，不记录音频或识别文本。

### A3. 此工作包的必过场景

- 空目录首次解压；第二次运行幂等；缺少任意一个文件；同尺寸但内容损坏；显式指定目录下文件齐全但损坏。
- exe 旁目录只读而用户目录可写；显式指定目录只读；目标文件被占用；模拟写入中断、校验失败和替换失败；两个进程并发修复。
- 当前模型与旧模型同时存在、仅旧模型存在、当前模型损坏但旧模型有效；每种情况都断言最终实际加载的路径。
- 使用带 embedded-models 的最终 exe 在隔离空目录跑 --self-check，并在故意损坏一个文件后再次执行修复与自检。

## 3. 工作包 B：控制层、录音焦点与设置事务

涉及 apps/tray/src/ui_main.rs、settings.rs、settings_web.rs、settings.html、crates/inject。此包完成后，HTML 不得直接决定业务是否成功。

### B1. 类型化动作与结果

- 定义 UiAction：SetMode、SetHotkey、SetAutostart、RequestRecord、CheckUpdate、FetchAnnouncement、RepairModels。定义 UiResult 或等价状态：请求编号、动作种类、Running、Succeeded、Failed、用户可见消息。
- IPC 入口只负责 JSON 解析、字段校验和分发。未知 action、无效数值、重复提交返回明确失败，不能静默忽略。控制层完成动作后只发送一个最终结果；界面按钮在 Running 时防重复点击。
- 主线程 App 状态更新集中在控制层；异步任务通过 PostMessage 返回，不在 WebView 回调里执行大文件校验、网络请求或长时间阻塞。避免在持有 APP 的 RefCell 可变借用时显示模态框或进入可能重入的 WebView 回调。
- WebView 页面只接收经过 JSON 序列化的状态，动态文字只用 textContent。限制导航至内嵌页面，外部地址不得获得 IPC 权限。

### B2. 录音与注入目标规则

- 将首页“开始录音”按钮改为“返回目标应用后按快捷键”动作：点击只隐藏设置窗口并提示当前热键，不直接启动录音。没有可靠目标窗口时不得自动注入。
- 全局热键开始录音时记录当时的外部前台目标窗口；VoiceType 自身窗口、已销毁窗口和不可注入窗口不得作为目标。托盘菜单关闭后恢复之前的外部前台窗口。
- 每次混合模式中间结果和最终提交前确认目标仍是同一可用窗口。焦点移走后不得向新窗口继续键入、粘贴或退格；记录“目标已切换”，保留最终识别文本供用户明确操作，不自动在新目标上补写。对已经输入到旧窗口的中间文本，只在能够安全确认原目标与输入位置时清理；否则提示用户处理，禁止盲目退格。
- 使用两个不同目标窗口进行真机测试：从 A 启动录音、中途切到 B、结束录音，B 始终不得收到 VoiceType 输入或退格。粘贴、逐字键入、混合三种模式都要覆盖。

### B3. 热键与自启事务

- 热键先校验并试注册新组合，保存注册表，全部成功后才提交 UI 状态；任一步失败恢复旧注册、旧内存状态和旧显示。若旧热键恢复也失败，给出明确高优先级错误，不显示“已应用”。
- 浏览器键盘事件不要把任意 event.keyCode 直接当 Win32 VK。定义受支持键位映射及修饰键规则；中文输入法、AltGr、纯修饰键、系统保留组合、非法码必须明确拒绝或按文档处理。原生备用窗口使用同一套热键校验。
- 自启读写以实际 HKCU Run 和旧快捷方式迁移结果为准。启用、禁用、注册表失败、旧快捷方式删除失败均有明确回执；失败后重新读取并展示实际状态。
- 测试热键冲突、注册成功但保存失败、重启后仍生效、旧键恢复失败、非法输入；测试自启启停和失败后状态。测试使用隔离的注册表适配器，真机冒烟使用专用测试用户，不改开发者的个人设置。

## 4. 工作包 C：窗口可用性、更新结果与运行时依赖

涉及 settings_web.rs、settings.html、ui_main.rs、updater.rs、README.md、scripts/installer.iss。

### C1. 可见且持久的结果

- 更新事件区分 CheckUpdate 与 FetchAnnouncement，不能共用一个无类型文本再由“窗口是否可见”猜用途。
- 检查更新的最新、发现新版、下载失败、通道失败四种结果均在当前页面显示持久状态；从托盘触发时使用托盘气泡或打开对应页，不能只写入隐藏页面。新版本准备完成时保留现有用户确认和重启流程。
- 公告结果保存到“更新与关于”页，同时在其他页面显示“公告已更新”的可见提示；失败也要可见。关闭并重新打开窗口后，最近一次结果仍可查看，直到下一次请求替换。
- 手动模型修复的 Running、成功和失败状态留在模型区；短暂 toast 只能辅助提示，不能作为唯一证据。

### C2. 窗口、DPI 与无 WebView2 场景

- 用 GetClientRect 得到的实际客户区尺寸设置 WebView；在 WM_SIZE、WM_DPICHANGED 和显示器切换后同步更新子窗口。HTML 去掉会强制裁切的固定最小宽高，内容允许滚动，按钮和文字在 100%、125%、150%、200% 缩放下均可访问。
- 明确 DPI awareness manifest 和支持矩阵；在 1920×1080 与 1366×768、单屏与双屏、高对比度和键盘导航下检查窗口。
- WebView2 Runtime 缺失或创建失败时，显示可操作的原生备用设置窗口。备用窗口至少具备注入模式、热键、自启、模型状态／修复、检查更新／公告六类功能，并调用同一控制层；不复制模型、热键或更新的业务逻辑。诊断日志记录 WebView 创建失败原因。
- 安装版和便携版均验证有 Runtime 与无 Runtime 的机器；无 Runtime 时核心功能与设置仍可用。README 写清现代界面的 Runtime 条件、备用界面行为和故障排查位置。
- 测试窗口首次打开、关闭隐藏、再次打开、最小化恢复、WebView 创建失败、Runtime 缺失、进程退出后的清理；每个场景确认托盘热键与录音仍正常。

## 5. 工作包 D：提交阶段门禁和测试基础设施

新增 .github/workflows/ci.yml，并扩充 release.yml、scripts 下的测试工具。所有新增测试必须验证外部可观察行为或失败路径，不能重复实现代码的判断式来“证明”代码正确。

### D1. 每个提交必须过的 CI

- pull_request 与 push main 都执行 Windows 构建；安装固定 Rust toolchain 组件 rustfmt 和 clippy，执行 cargo fmt --all -- --check、cargo clippy --workspace --all-targets --locked -- -D clippy::all、cargo test --workspace --locked、Python unittest、HTML/JS 的 DOM 交互测试、git diff --check。现有 LNK4098 链接器警告须单独追查 C 运行库来源并记录结论，不能把它误当成新增 Rust 代码的 clippy 结论。
- 同一 CI 再执行 prepare-models、带 embedded-models 的 release 构建、隔离模型目录中的最终 exe --self-check、完整 package.ps1（含 Inno Setup）、verify_release.py --dist。每次用唯一空输出目录，package.ps1 与 installer.iss 必须接收同一个目录，禁止用旧 dist 文件补齐缺失产物。
- 新建 ui-tests/package.json 与 package-lock.json，CI 固定 Node 主版本后执行 npm ci --prefix ui-tests 和 npm test --prefix ui-tests。DOM 测试模拟 IPC，验证按钮动作、状态渲染、隐藏页更新结果、错误提示与键盘输入；不能只运行 JS 语法检查。
- CI 上传测试报告、打包文件名、SHA-256 与失败日志。网络下载类瞬时故障可以在确认原因后重跑失败 job；逻辑失败、UI 测试不稳定、缺少工具或未运行测试一律算失败，不能通过重跑绕过。

### D2. 可交互 Windows 桌面验收

- 建立一次性 Windows 测试虚拟机或可交互专用 runner，保证测试进程和 UI 自动化处于同一登录桌面会话。测试脚本先校验桌面会话；找不到主窗口时输出进程、会话、窗口与诊断日志，再失败退出，不能报告“UI 通过”。
- scripts/gui_smoke.ps1 接收 -PortableExe、-InstallerExe、-ReportDir 三个绝对路径参数，启动待测最终 exe，使用隔离 LOCALAPPDATA、模型目录和专用用户设置；按超时等待真实窗口，再通过 UI Automation 操作控件和核对可见文本。结束时只清理已验证位于隔离目录的文件与自身进程。
- 自动场景至少覆盖：托盘打开／隐藏／重开、三种模式、热键冲突与回滚、自启切换、模型损坏修复、最新版本与公告展示、无 WebView2 备用界面、DPI 尺寸、录音目标焦点。涉及麦克风与目标应用的测试在专用虚拟音频／文本目标上运行；无法自动化的硬件场景列入第 8 节人工验收，不能省略。
- GUI 冒烟必须针对 CI 产出的 exe 和安装包，而不是工作区里可能陈旧的 dist。

### D3. 测试隔离

- Rust 模型测试不再通过并行测试共享的全局环境变量切换路径；把根目录作为依赖注入参数。注册表、文件系统故障和更新网络使用可替换适配器。所有测试有唯一临时目录、确定性清理和超时。
- 为每个已发现缺陷加入回归测试，测试名说明失败场景。先让测试在旧实现上失败，再修代码使之通过；审查时保留失败前后的测试记录。

## 6. 工作包 E：发布契约与版本准备

目标新版本定为 0.8.0；截至本文编写时 v0.7.0 已存在，v0.8.0 尚不存在。本工作包在 A 至 D 全部通过后执行，不能提前打 tag。

- apps/tray/Cargo.toml 改为 0.8.0，执行 cargo build -p voicetype-tray 刷新 Cargo.lock；app_update.json.history 头部插入 0.8.0 公告，body 按【新增：…】【修复：…】【变更：…】写用户能理解的变化。
- 本地运行 verify_release.py --tag v0.8.0；检查远端没有同名 tag。版本门禁同时检查 tag、Cargo 版本、公告头条，以及 tag 指向的提交确实含这些文件。
- workflow_dispatch 先在待发布提交上生成完整测试产物但不创建 Release；执行本地两种形态的更新助手模拟和安装／卸载检查。六个资产必须是三个产物及各自同名 .sha256；清单为 ASCII，格式为 64 位小写 SHA-256、两个空格、文件名和换行。
- 修正 package.ps1 的 OutDir 参数与 installer.iss 的 OutputDir：Inno Setup 输出目录由打包脚本显式传入，三个产物必须落在同一个唯一空目录。增加含空格路径的打包测试，并在安装包缺失时立即失败；不得从默认 dist 捡取旧安装包。
- 便携 zip 必须仅有 voicetype-tray.exe、README.md、app_update.json；不得含 install.mode。安装包必须写 install.mode；两者内的 exe 与裸 exe 一致，且均通过内置模型自检。安装版自启设置与 UI 使用同一 HKCU Run 值。
- 保持 updater.rs 的 GitHub Release URL 前缀验证与两次 SHA-256 校验。资产名或路径优先级如需调整，必须先更新协议测试和本文件的发布验收，不能单点改名。

## 7. 实施顺序与每阶段交付

按顺序执行，不并行合入互相依赖的半成品；每阶段结束把测试记录附在变更说明中。

1. 阶段 0：建立 codex/quality-recovery 分支，保留当前工作区修改的可恢复快照；列出本文所有验收场景与当前失败证据。推送分支并建立审查入口以运行 PR CI；只冻结范围，不碰发布版本或 tag。
2. 阶段 1：完成 A；提交模型状态、事务修复、故障注入测试。门禁：A3 全部通过，已有模型路径与旧模型兼容不退化。
3. 阶段 2：完成 B；提交控制层、焦点规则、热键和自启事务。门禁：双窗口注入测试与事务失败测试通过。
4. 阶段 3：完成 C；提交窗口尺寸、结果展示、原生备用界面及 DOM 测试。门禁：有／无 WebView2 和多 DPI 的桌面验收通过。
5. 阶段 4：完成 D；提交持续集成和桌面测试脚本。门禁：同一待发布提交的所有 CI job 与桌面验收为绿；任何不可运行项阻止继续。
6. 阶段 5：完成 E；在分支提交并推送 0.8.0 版本和公告，等待 PR CI。合入 main 后记下最终提交 SHA；如果合入产生新 SHA，必须在该 main SHA 上重新运行全部发版前门禁并重建候选资产。第 8 节标为“发版前”的项目全部对应最终 main SHA 并签收后才推 tag。
7. 阶段 6：确认 main 已推送，创建指向该已验收 SHA 的 v0.8.0 tag 并推送，盯完 release 工作流，完成第 8 节标为“发版后”的项目、第 10 节线上验收与证据归档，随后才宣布本轮完成。

每个阶段允许修改其覆盖文件及必要的接口调用方；不允许为了“顺便优化”扩大功能范围。若发现新的 P0/P1/P2 缺陷，先加入本文对应场景、写能复现的测试，再修复；不得只修表面症状。

## 8. 验收清单与门禁阶段

8.1、8.2、8.4 和 8.3 的“发版前”项目必须在打 tag 前通过；任一项失败即 No-Go。8.3 的“发版后”项目只能在 Release 产生后执行；它们未通过时不得宣布完成，按第 10 节处理，不得假称发版前已实测线上热更新。

### 8.1 模型和识别

- [ ] 默认目录、显式目录、只读目录、旧模型目录均按 A1 规则选择，界面展示的目录就是实际加载目录。
- [ ] 空目录、缺文件、同尺寸损坏、替换失败和并发修复的测试全部通过；损坏文件绝不显示 Ready。
- [ ] 最终便携 exe 与安装版 exe 在隔离空目录运行 --self-check 成功；真实 ASR 和 VAD 初始化成功。
- [ ] 修复期间 UI 可响应；失败状态可见且有诊断，不误报“已就绪”。

### 8.2 主界面与输入

- [ ] 有 WebView2 时现代界面正常；无 Runtime 或创建失败时原生备用界面可完成全部关键设置。
- [ ] 100%、125%、150%、200% 缩放和 1366×768 屏幕上所有内容可见或可滚动访问；打开、隐藏、重开不丢状态。
- [ ] 首页按钮不会在 VoiceType 窗口中启动注入；热键从目标 A 启动可输入 A，切换到目标 B 后 B 无误输入、无误退格。
- [ ] 三种注入模式、热键冲突、保存失败回滚、重启后持久化、自启启停均有自动或真机证据。

### 8.3 更新与发布

- [ ] 发版前：最新版本、可下载新版、下载失败、公告成功与失败，从更新页或托盘触发、结果返回时分别停留在首页／偏好页／更新页，均给用户可见结果；网络场景使用可控测试源，不放松生产 URL 白名单。
- [ ] 发版前：0.8.0 代码版本与公告头条一致；远端尚无 v0.8.0 tag；预发布构建的三个产物及三份 SHA-256 清单齐全并通过校验，便携 zip 内容与裸 exe 一致，install.mode 只在安装版。
- [ ] 发版前：本地模拟便携换 exe 和安装版静默重装，均能重启并保留既定的自启与热键设置；全部 CI、完整安装包、可交互桌面冒烟与人工麦克风验收的证据对应同一提交和同一组预发布产物。
- [ ] 发版后：v0.8.0 tag 指向已验收提交，Release 公告正文与 app_update.json 一致，线上六个资产齐全且清单逐一通过。
- [ ] 发版后：真实便携版从 0.7.0 热更到 0.8.0 后自动重启；真实安装版静默重装后自动重启，自启状态保留；证据记录最终线上资产的 SHA-256。

### 8.4 质量门禁

- [ ] cargo fmt、clippy、Rust 默认与 embedded-models 测试、Python 测试、DOM 测试、GUI 冒烟、release 构建、package.ps1、verify_release.py 全部通过，无跳过。
- [ ] 安全边界检查通过：URL 白名单、双重 SHA、固定资产名、模型内置、目录优先级和形态标记没有弱化。
- [ ] 代码审查无未解决的 P0/P1/P2；P3 若保留，必须在发布说明中写明影响和处理时间，不得把本清单项目降级为 P3。

## 9. 证据与失败处理

为每次候选发布保存一份 qa/evidence/v0.8.0.md，至少记录：提交 SHA、构建环境、CI 链接和 job 结果、每条命令与退出码、六个资产的文件名／大小／SHA-256、模型自检目录与退出码、GUI 测试机器和 DPI、便携／安装版更新前后版本、截图或日志位置、验收人及日期。音频和识别文本不得进入日志或公开证据。

候选发布的命令顺序固定如下。第 5 步的 DOM 测试脚本与第 9 步的 GUI 测试脚本须在 D 工作包中实现并写入仓库；脚本不存在或无法运行就是门禁失败。

1. cargo fmt --all -- --check
2. cargo clippy --workspace --all-targets --locked -- -D clippy::all
3. cargo test --workspace --locked
4. PowerShell 执行 scripts/prepare-models.ps1，再执行 cargo test -p voicetype-tray --features embedded-models --locked
5. python -m unittest discover -s scripts -p 'test_*.py'；随后执行 npm ci --prefix ui-tests 和 npm test --prefix ui-tests
6. python scripts/verify_release.py --tag v0.8.0
7. 在 target 下创建唯一空的 release-candidate-运行编号目录，执行 scripts/package.ps1 -OutDir 该目录；不得使用 SkipInstaller，也不得用已有 dist
8. python scripts/verify_release.py --tag v0.8.0 --dist 第 7 步目录；对该目录的 voicetype-tray.exe 在隔离空模型目录运行 --self-check 并检查退出码
9. 在可交互 Windows 测试虚拟机运行 scripts/gui_smoke.ps1 -PortableExe <第 7 步裸 exe 的绝对路径> -InstallerExe <第 7 步安装包的绝对路径> -ReportDir <隔离报告目录>；随后完成人工麦克风与双形态本地更新助手模拟。真实线上热更新只在第 10 节发版后执行

第 7 至 8 步在仓库根目录的 PowerShell 示例（仅在 E 工作包修复 OutDir 后使用）：

    $candidate = Join-Path (Resolve-Path -LiteralPath target).Path ("release-candidate-" + [Guid]::NewGuid().ToString("N"))
    if (Test-Path -LiteralPath $candidate) { throw "候选目录不是空目录" }
    & ./scripts/package.ps1 -OutDir $candidate
    if (-not $?) { throw "完整打包失败" }
    python scripts/verify_release.py --tag v0.8.0 --dist $candidate
    if ($LASTEXITCODE -ne 0) { throw "发布资产验证失败：退出码 $LASTEXITCODE" }

每条命令都记录开始时间、结束时间、退出码、所用提交 SHA 和日志路径。PowerShell 包装外部命令时显式检查退出码；不得只以最后一条 Write-Host 成功推断构建成功。第 7 步需要 Inno Setup，未安装时先安装到测试环境，不得改用 SkipInstaller 声称完整发布通过。

测试失败时先写复现步骤与预期／实际结果，归入本文相应工作包；修复后运行该场景及其上下游场景，再跑全部门禁。任何“仅在本机通过”“CI 未运行”“安装包尚缺”“桌面不可用”的候选版本都保持 No-Go。失败证据保留，不删除后只展示绿色结果。

## 10. 发布、线上确认与回退

1. 在第 8 节全部“发版前”项目对最终 main SHA 签收后，按 AGENTS.md 顺序确认提交已推送，再创建和推送指向该 SHA 的 v0.8.0 tag。tag 构建失败先查明原因；确认为网络瞬时错误才用 rerun-failed-jobs，逻辑失败必须改代码并使用新的补丁版本，不能强推覆盖既有 tag。
2. Release 完成后确认六个资产、公告正文与清单；用上一版便携和安装版分别点击“检查更新”，确认下载、校验、替换／静默重装、自动重启及版本显示。验证失败不得宣布完成。
3. 如发布前失败，停止打 tag，回到对应阶段修复。如已发布后发现阻断缺陷，保留原 tag 和资产作审计，立即停止推广，并以 0.8.1 或更高新版本修复和重新完整验收；不得覆盖 v0.8.0 资产或放松校验。更新通道先行导致资产未就绪的提示属于现有协议预期，仍须监控到资产齐全。
4. 最终交付给用户：代码变更摘要、通过的命令和真机结果、Release 链接、已知限制、qa/evidence/v0.8.0.md。若任一必要项未完成，明确报告阻断点和下一步，不使用“已全部测试通过”的表述。

## 11. 执行中的硬规则

- 每个修复必须先有失败复现，再有对应回归测试，最后跑完整矩阵。修复一个场景不能改变另一个场景的既定行为而不更新测试和文档。
- 主线程不做网络、模型写入、长时间散列或识别引擎初始化；UI 所有异步结果必须有可见终态。
- 不把模型文件存在、文件校验通过、引擎可初始化三个概念混用；不把“WebView 页面收到 JS”当成“用户看到了结果”。
- 不以本地旧 dist 或已存在 tag 充当本次发布证据；不把编译、自检和单元测试通过推断为 GUI、安装版或热更新通过。
- 发布流程和本文冲突时，优先保持 AGENTS.md 中资产协议、安全边界与版本一致性不变量；先修订本文再执行新的流程。
